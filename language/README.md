# Mira: короткая карта действующего языка

Открывайте только пример нужной возможности. Это проверяемый код, а не отдельная спецификация языка.

Для первых шагов достаточно функций и простых выражений. Рабочий файл — `examples/first-graph`:

```mira
double(value) = value * 2
space Main:
  number = 3
  result = double()
  number.out -> result.value
```

`double` — имя функции, `value` — её вход, выражение после `=` — результат. Здесь тип целого выводится автоматически. `number` и `result` — ячейки внутри пространства Main. Стрелка передаёт выход `number.out` на вход `result.value`, поэтому результат равен6. Имена выбираете вы; числовые ID не нужно придумывать или запоминать. Сначала измените3 на5, затем попробуйте `value * 2 + 1`. Вложенные пространства и нейронное обучение можно изучать следующими шагами, не одновременно со всем синтаксисом.

В нынешней MiraOS исходник можно открыть, изменить и сохранить; это ещё не означает исполнение изменений. Полная пересборка ОС внутри редактора пока не готова. На хосте этот файл можно запустить: `target/debug/mira run language/examples/first-graph`. Проверка примера и понятной ошибки для неверного вызова — `language_examples::beginner_graph_example_runs_and_explains_misplaced_arguments`.

Host-компилятор проверяет текст командой `target/debug/mira check PATH`, а `target/debug/mira run PATH` выполняет этот пример и выводит `Main/result = 6`; `run-miraos.sh --build` собирает ОС на хосте. При обучении всегда уточняйте, где выполняется конкретный шаг.

Из корня: `target/debug/mira check language/examples/structure`; для структуры исходников — `mira source INPUT list/read`; для связей и портов — `mira inspect INPUT card ID`. Перед изменением примера прочитайте соответствующий тест. Его ожидаемый результат — свидетельство реально проверенной возможности.

Вызов `cells.store.increment()` выбирает локальную операцию определения store и связывает её с экземпляром store. `cells.parent.store...` явно использует Z-область родительского экземпляра. `graph.parent.rate()` выбирает его графовый выход. Это тот же механизм исполнения; операция не требует отдельной runtime-ячейки. Пример state проверяет сохранение состояния между активациями и нативную компиляцию.

Не путать: вложенная функция — определение кода; ячейка в space — экземпляр; принадлежащее экземпляру space — его графовое Z-пространство. Одно определение может использоваться несколькими экземплярами. Физическая упаковка исходников не создаёт ни определений, ни экземпляров. Не выдавать изменение одного уровня за изменение другого.

Если нужной возможности здесь нет, найдите её определение/тест точечным поиском. Отсутствие в этой короткой карте не доказывает отсутствие в языке. При изменении языка обновляйте соответствующий пример и его проверку вместе.

Тип параметра можно не писать: `scale(value) = value * 2.0` выводит f32. Аннотация `_` также означает вывод. Это мономорфный вывод: одна функция получает одну согласованную сигнатуру, не неявный порт «любого типа» и не обобщённую функцию. Неоднозначное `identity(value) = value` требует вызывающего контекста, аннотации или проверенного предложения. Черновик `value + ?adjustment` сохраняет незавершённое выражение; его нельзя исполнять или компилировать. `inference::fill` проверяет заполнение целой программы, не подставляет скрытые нули.

Нативный рабочий цикл в MiraOS: Alt+X → `source open NAME/ID`, затем редактирование и Alt+X → `source compile` или `source run`. Выбранная функция задаёт точку входа (без параметров, результат i64/f32/bool/unit). Неизвестное имя детерминированно ищется в существующем индексе соседних исходных объектов с тем же лексическим родителем; нужная функция или тип включается в снимок компиляции. Затем так же разрешаются зависимости этих определений. Импортов и ручного списка зависимостей нет. Исходный порядок, идентичности и вложенные определения сохраняются; для явного пути вроде branch.finish подключается branch с его детьми. Чужое приватное определение с совпадающим именем не становится видимым. Общий снимок ограничен256KiB и прежними128 функциями/32 типами; исходники пользователя не склеиваются и не изменяются. Автоподбор требует объектов, уже видимых в source index (с явными идентичностями); неявные вложенные определения внутри включённого объекта остаются допустимы.

Результат или ошибка показываются в OUTPUT; Escape скрывает панель, позиция/правки сохраняются. Ошибка указывает абсолютный байт в исходном проекте, а не смещение в собранном снимке. Повторный запуск неизменённого проекта/выбора использует готовый код; изменение любой части draft, в том числе соседнего helper, отменяет незавершённую сборку и требует новой. `source run` автоматически компилирует при необходимости. Внешние компоненты, поиск через пропущенные родительские области и графовые cells.* пока не подключены; это не общий графовый frontend. Все тела включённых объектов проверяются до исполнения; Raw addr/load/store запрещены, общий бюджет100000 операций, действуют штатные stack/arena/bounds/overflow guards. f32 показывается компактной научной записью. Код исполняется нативно из отдельного буфера и не заменяет работающие определения ядра. Ctrl+S сохраняет исходник, а не машинный код; после перезагрузки требуется новая компиляция. Это ещё не сборка всей MiraOS изнутри.

Инструменты bootstrap-хоста (не команды нативного редактора):

- `mira source language/examples/incomplete analyze` — сигнатуры и допустимые типы незавершённых мест.
- `mira source SOURCE learn MODEL CHOICE_JSON accepted` (или `rejected`) — явный обучающий пример; при отсутствии MODEL создаётся обычный System с весами. JSON одного выбора: `{"target":{"Parameter":{"definition":2,"index":0}},"ty":"Bool"}`.
- `mira source SOURCE suggest MODEL` — ранжированные предложения для неоднозначных типов; исходник не меняется.
- `mira source SOURCE resolve CHOICES_JSON OUTPUT` — проверить массив таких выборов и сохранить отдельный завершённый исходник. Предложения не заменяют проверку, не исполняются автоматически и не заполняют `?` сами.

`reflect.code_count(definition)`, `code_kind(definition,index)`, `code_child_count`, `code_child(definition,index,slot)`, `code_value`, `code_name_byte` исследуют существующее дерево выражений. Индексы — preorder внутри определения, действительны для его текущей версии. Виды: hole=0, integer=1, float=2, bool=3, unit=4, name=5, unary=6, binary=7, call=8, choose=9, construct=10, view=11, field=12, index=13. `code_value` возвращает целое/биты f32/0 или 1; неподходящий запрос возвращает -1. Доступны также definition_count/definition_at, parameter_count/parameter_type/result_type. Коды типов: unresolved=0, i64=1, f32=2, bool=3, event=4, unit=5, addr=6, data=7.

Внутри macro: `meta.quote(definition,index)` захватывает цель, `meta.integer(value)`, `meta.boolean(0_or_1)`, `meta.float_bits(bits)`, `meta.parameter(definition,index)` создают выражения; `meta.binary(operation,left,right)` объединяет их; `meta.replace(target,value)` добавляет правку в существующую транзакцию. Операции: add=0, sub=1, mul=2, div=3, eq=4, lt=5, and=6, or=7. Значения — локальные дескрипторы расширения, не runtime-ячейки. Перенос захваченного выражения из его лексической области запрещён; ссылки на параметры проверяются на захват. Это ограниченные преобразования без введения новых связываний, не полноценная система гигиенических макросов. Макрос может заполнить `?label` до итогового вывода типов/проверки; незаполненные места всё равно блокируют публикацию. Вся публикация откатывается при ошибке проверки.

Частичная самокомпиляция: `compiler @258 → scalar_parse` разбирает ограниченное тело функции, `compiler.scalar_check` детерминированно проверяет/выводит типы, `compiler.scalar_emit` создаёт x86-64 код. Работают i64/bool/unit, локальные переменные/const, присваивания, if/else/else if, while, for по диапазону, вызовы и рекурсия. Примеры: `examples/bootstrap`, `bootstrap-blocks`, `bootstrap-loops`, `bootstrap-nested-loops`, `bootstrap-calls`. Области видимости, определённость локальных переменных, неизменяемость параметров/const/индекса for и точные сигнатуры вызовов проверяются до генерации кода. Неоднозначный тип не превращается автоматически в i64. Последовательность операторов строится сбалансированно: длинный плоский блок не расходует глубину как вложенное выражение. Проверка module_tests содержит128 последовательных ветвлений. Ограничения переносимого шага: 16 входов, 48 локальных связываний, 256KiB входного модуля (host-мост отдельного word-тела сохраняет16KiB), 4096 токенов/узлов, 32 уровня разбора. Это не общие лимиты MiraOS или разрядности языка.

Host frontend преобразует принятый скалярный разбор в существующие Core Statement/Expr. Обычные build/build-kernel/build-uefi используют Mira-emitter для допустимых тел (до512 операторов и 2000 выражений). Проверенные операции с records/arrays понижаются к тому же word ABI через типизированные runtime-операции: конструкторы, чтение полей/индексов, запись i64/bool. Пример `examples/bootstrap-data` проверяет порядок побочных эффектов при составном присваивании. Типы и bounds checks сохраняются; неподдержанные операции остаются в действующем общем backend, без fallback при ошибке уже принятого профиля. Полный frontend, понижение агрегатов, общая композиция/checker/linker и runtime-операции пока реализованы на Rust.

Генератор пишет в bounded ScalarBytes (1048576 байтовых элементов), одинаковый в VM/native. Внутренний raw entry принимает контекст: 16 входных 64-битных слов и ошибку по смещению128. Это не замена общего ABI языка. Адаптер сохраняет стековый ABI, stack/fuel checks и общие traps. Межфункциональные rel32-релокации связываются общим linker; cache хранит шаблоны без адресов/идентичностей и повторно привязывает целевые ID. Проверки `bootstrap_native` покрывают вызовы/рекурсию, циклы, порядок записи и traps. `sys.address_of(record.field)` / `sys.address_of(array[index])` возвращают адрес проверенного места в native-профиле; обычная portable VM не выдаёт адреса хоста, scratch не разрешает утечку временного адреса. `sys.procedure_by_id(id)` ищет процедуру по идентичности из таблицы скомпонованного образа и возвращает нулевой addr при отсутствии; для известного имени остаётся `sys.procedure_address(name)`. Это native-адреса, не portable-дескрипторы AST; пример `examples/system`.

`native_scalar_compiler` — отдельная конечная UEFI/QEMU-проверка: компилирует и вызывает10 функций из собственных исходников compiler. Постоянные графовые буферы хранят вход/результат, sys.scratch освобождает временный разбор; публикация и вызов кода выполняются снаружи scratch. Сканер читает многострочный исходник через окна4096 байт, корректно завершает //-комментарий на newline. Нативный компилятор ещё не встроен в редактор; весь язык сам себя пока не собирает.

`compiler @258 → module_index/module_emit/module_link` читает несколько скалярных определений из неизменённого текста, собирает точные сигнатуры и исходные диапазоны, сохраняет явные/неявные идентичности, компилирует тела существующим scalar-компилятором и связывает forward/recursive calls. Пример `examples/bootstrap-module`; проверка `bootstrap_scalar::module_tests` запускает полученный ELF с результатом88. Вызовы с неверными типами, дубли имён/ID, отсутствующая функция и неверная точка входа блокируют публикацию. Этот module-профиль принимает обычные имена без backticks и явные сигнатуры (i64/f32/bool/addr/номинальный Data на входе, i64/f32/bool/unit/addr или заимствованный номинальный Data на выходе); это ограничение module-драйвера, не отказ от общего inference. Драйвер ограничен128 определениями,262144 байтами общего текста и1048576 байтами связанного кода. `module_link` задаёт общий положительный бюджет операций: внутренние вызовы/рекурсия его не сбрасывают. Бесконечный цикл проверен завершением по бюджету. Код остаётся независимым от ОС; `module_elf` отдельно упаковывает его для host-проверки. Общий `elf_header` на Mira используется и обычной native-сборкой; прежний Rust-сериализатор ELF удалён. Kernel/UEFI используют свои существующие загрузочные форматы.

Module-профиль читает номинальные массивы i64/f32/bool и структуры с i64/f32/bool или ссылками на уже объявленные типы. Работают конструкторы, поля, `.len`, индексы, запись/составное присваивание, передача объектов и локальные определения/типы после тела функции. Типы сначала индексируются во всём исходнике; видимость функций и типов определяется лексическим владельцем. Имена функций уникальны внутри своей области; одинаковые короткие имена в разных вложенных областях допустимы. Примеры `bootstrap-arrays`/`bootstrap-records`/`bootstrap-nested` дают83/1128/6 в Core VM и полученном ELF. Ссылочные поля задаются конструктором и пока не переназначаются; возвращать можно i64/f32/bool/unit/addr и проверенные заимствованные Data-ссылки (см. bootstrap-borrowed). Созданные внутри функции временные объекты пока не могут покидать её регион; это ограничение переносимого профиля, не новая глобальная семантика Mira. Адресные операции остаются явным низкоуровневым доступом. `bootstrap-addresses` проверяет addr, unsigned-сравнения, проверяемый sys.offset и явные math.wrapping_add/mul; sys.store8 поддержан для собственного emitter. Начальные записи со ссылками требуют явных значений. До32 типов/полей,16 параметров,128 функций; общая графовая композиция и остальные тензорные операции ещё не перенесены. Общий layout-лимит объекта —1048576 слов; реальное выделение дополнительно ограничено конкретным регионом памяти.

`examples/bootstrap-floats` проверяет переносимый module-профиль: литералы `0.5`, `-0.0`, `1e-45`, параметры/результаты f32, локальный вывод, массивы/поля f32, `+ - * /`, сравнения и составное присваивание. Доступны `math.bits/from_bits/to_f32/sqrt`. Неявного смешивания i64 и f32 нет; `%` и битовые операции требуют i64. Результат примера37 совпадает в Core VM и скомпилированном ELF. Нефинитные значения запрещены, деление на ±0 даёт ошибку деления. Внутренний ABI хранит канонические биты binary32 в одном слове; это не новый публичный ABI. ELF-обвязка устанавливает MXCSR для округления к ближайшему с чётным при равенстве и без сброса малых чисел; raw-модуль использует FP-состояние вызывающей системы, как существующий native runtime.

`compiler.parse_float(text,length,result)` преобразует беззнаковую десятичную запись в биты f32 целочисленными операциями на Mira: точное округление, включая subnormal и границу переполнения. Статусы0/1/2 — успех/синтаксис/нефинитный результат; при ошибке result не меняется. Знак применяет грамматика, сохраняя -0.0. Лимит128 байт на числовой токен общий с integer decoder; чрезмерно длинный литерал отвергается явно. Обычный host frontend вызывает тот же Mira decoder для выражений и координат; Rust-разбор остаётся только в явном stage-zero seed. Проверки: bootstrap_literals (точные границы и округление), `tests/bootstrap_literals.rs`, native self-build (исполнение пересобранного decoder).

`examples/bootstrap-tensors` проверяет перенос в тот же module-профиль: `tensor[f32,2,2]`, до8 положительных осей и1048576 элементов, плоские индексы, `.len`, передачу параметров и обычные конструкторы. Поддержаны также i64/bool тензоры. Массивы остаются rank1; для групповых операций совместимы разные номинальные типы с одинаковыми формой и элементом. Само объявление функции по-прежнему требует её номинальный Data-тип.

На Mira перенесены `tensor.fill`, `sum`, `copy_into`, `add_into`, `sub_into`, `mul_into`, `div_into`, `scale_into`, `matmul_into`. Арифметика/sum/fill требуют f32; copy сохраняет также i64/bool. Совпадения числа элементов недостаточно: формы `[2,2]` и `[4]` различаются. Аргументы вычисляются слева направо один раз. Поэлементные операции допускают совпадение целого выходного объекта с входным; views в module-профиль пока не перенесены. Цикл исполнения расходует общий fuel на каждый элемент и использует прежние ошибки f32; это не самостоятельная транзакция и не новое обещание real-time. Данные/время жизни/ограничения региона те же, что у массивов. Элементарные операции и проверка формы работают на Mira, не вызывают Rust tensor lowering входной программы.

`tensor.matmul_into(output,left,right)` принимает f32-матрицы rank2. Если left имеет форму `[M,K]`, right — `[K,N]`, то output должна быть `[M,N]`. Несовместимые формы отвергаются до генерации кода. Обе входные матрицы могут быть одним объектом, как в A×A; выход должен быть другим объектом. Проверка идентичности выполняется перед первой записью и даёт прежнюю ошибку invalid при нарушении. Внутренняя ось суммируется по порядку с обычными f32 умножением/сложением, без переупорядочивания/FMA; fuel расходуется на каждое слагаемое. Используется32 байта временного стека; отдельной копии матрицы нет. Это контракт текущего private module ABI без views, не проверка произвольных указателей/пересекающихся unsafe областей.

Пример даёт41 в Core VM и native ELF: reference @3 вычисляет матричное умножение циклами, multiply @5 вызывает matmul_into, run @4 проверяет оба. Тот же пример внутри native self-build компилируется вторым экземпляром компилятора; затем вызывается multiply с совпадающими входом/выходом и проверяются ошибка и неизменность всех четырёх слов данных. Дополнительные module_tests проверяют прямоугольные формы, порядок f32, переполнение, fuel, неправильные размеры/rank/элемент и обе выходные aliases. Tensor AD и persist/views ещё требуют переноса. Один native self-build тест дополнительно поручает пересобранному компилятору собрать и выполнить этот пример в UEFI. Это не сборка всей MiraOS внутри её редактора.

`examples/bootstrap-relations`: `relation.messages_into(output,links)` и `relation.aggregate_into(output,links,messages)` теперь разбираются, проверяются и компилируются на Mira. Links — обычная запись с полями sources/targets (f32 rank2), source_indices/target_indices (i64 rank1 с одинаковым числом рёбер). Имена полей значимы, порядок свободен. Необязательные active (bool rank1) и features (f32 rank2) проверяются по числу рёбер. Messages имеют форму `[edges,source_width]`; aggregate требует именно объявленный номинальный тип targets и сообщения `[edges,target_width]`.

Сначала проверяются оба индекса каждого активного ребра, до любых выходных записей. Неактивные рёбра могут иметь недопустимые индексы: messages пишет для них нули, aggregate пропускает их. Messages запрещает output/sources identity, aggregate — output/messages identity; у aggregate targets могут быть выходом. Тот же invalid trap, bounded stack48 байт, fuel в проверках, обнулении и обработке элементов, прежний f32 порядок суммирования. Ошибка arithmetic/fuel после начала обработки требует внешней транзакции, если нужен rollback всего шага. Private module ABI пока не принимает views/произвольные overlapping unsafe области. Это перенос двух операций, не всей графовой композиции, пластичности или автономной системы обучения.

Пример даёт53 в Core VM и native ELF. Проверяются active/no-mask, порядок полей, формы optional-полей, номинальность target, invalid endpoints и запрещённые aliases. Native self-build вторым экземпляром компилятора собирает объединённый tensor/relation пример (verify @120); поздние повреждённые source/target indices дополнительно проверяются на неизменность восьми слов выхода до отказа.

`examples/bootstrap-plasticity` дополняет те же relation-записи:

- `relation.active_count(links)` проверяет активные endpoints и возвращает число активных рёбер. Без маски все слоты активны.
- `relation.neighbors_into(output,links,target)` возвращает число входящих соседей и пишет source indices в начало i64 rank1 массива достаточной ёмкости. Порядок — порядок слотов, дубликаты сохраняются, неиспользованный хвост не меняется. Все активные endpoints, target и output/index-array identity проверяются до записи.
- `relation.add_edge(links,source,target)` требует active bool mask, выбирает первый свободный слот и возвращает его индекс либо -1 при полном буфере. Предварительно проверяет активные endpoints, оба новых индекса и различие массивов source_indices/target_indices. Индексы пишутся до active=true; features остаются прежними.
- `relation.remove_edge(links,slot)` требует active mask, проверяет только номер слота, возвращает прежний флаг и выключает связь. Повреждённые endpoints допустимы: эту операцию можно использовать для удаления неисправной связи. Индексы/features сохраняются.

Это ограниченная структурная пластичность в уже выделенной ёмкости, без новой памяти, изменения числа слотов или записи immutable ссылочных полей. Scratch48 байт, существующие fuel/traps; active flag last не означает атомарную транзакцию или готовую SMP-синхронизацию. Внешняя neural_try нужна для отката нескольких действий. Неявного превращения всего Program/Space в relation-record нет. Пример даёт61 в Core VM и native ELF и добавлен в native self-build вместе с tensor/relation примерами. Проверки покрывают full/free slot, повторное удаление, исправление повреждённого ребра, prefix/tail neighbors, invalid endpoints/slot/target, запрещённые aliases и отсутствие active mask.

`examples/bootstrap-indexed` проверяет `tensor.gather_into(output,input,indices)`, `aggregate_into` и `normalize_rows_into`. Gather принимает f32 rank2 с равной шириной строк, i64 rank1 индексы и output.rows=indices.len; aggregate требует input.rows=indices.len. Индексы проверяются до записи; output/input identity запрещена. Выборка и суммирование используют тот же scalar_message_loop, что и типизированные relation-операции, без создания relation-записи или отдельного runtime. Порядок повторяющихся индексов сохраняется.

Normalize требует равные rank2/f32 формы, допускает output=input и вычисляет каждую строку как input/sqrt(sum(input²)). Сначала читается вся строка для нормы, затем пишется результат. При нулевой норме строка становится нулевой; f32 underflow/overflow и ошибки следуют прежним скалярным правилам (это не новый numerically-stable norm). Fuel расходуется и на норму, и на запись; scratch32 байта. Самостоятельного rollback нет, views не перенесены. Пример даёт67 в Core VM и native ELF. Проверки также покрывают неверный последний индекс/shape/rank/элемент, aliases, нулевую и малую норму, переполнение.

`examples/bootstrap-memory` переносит существующие sys.address_value, load8/16/32/64 и store8/16/32/64 в module-профиль. Адреса остаются Addr, числовые значения i64; узкие чтения расширяются нулями, узкие записи используют младшие биты. Пример memory @151 принимает как минимум16 доступных байт от вызывающей системы, проверяет ширины/смещения/сохранение битов; memory_run @152 проверяет только преобразования адресов и может исполняться в Core VM/ELF. Настоящие load/store проверяются в UEFI на выделенном буфере, включая неизменность следующего слова. Caller отвечает за допустимость/время жизни/синхронизацию адреса; это не безопасные ссылки, MMIO memory barriers или завершённый lifetime-контракт. Получение адреса временного Data через sys.data_address, memory_copy/fill и прочие sys операции в этот профиль ещё не перенесены.

`examples/bootstrap-paths`: outer.inner.leaf(value) разрешается по тому же дереву определений без импортов. Первый компонент подчиняется лексической видимости, последующие — непосредственные дети предыдущего. Нельзя пропускать уровень или находить чужую вложенную функцию по короткому имени. Record fields остаются обычными полями (pair.value). Пример даёт19 в Core VM/native ELF; смена пути на outer.branch.leaf даёт29. Отсутствующие/неверные пути и типы блокируются до emission. Короткое имя выбирает ближайшую лексическую область; пример различает две leaf в разных поддеревьях. Qualified type names/handler values и графовые cells.* ещё не перенесены; функция не получает замыкание/экземпляр состояния от наличия пути.

`examples/bootstrap-borrowed`: функция может вернуть входной массив/тензор/структуру, ссылочное поле входной структуры, локальный псевдоним входа или выбор между входами. Рекурсивные вызовы используют тот же контракт. Временный регион каждого вызова по-прежнему освобождается при возврате; новый объект из этого региона возвращать нельзя (ошибка10), в том числе через другую функцию, ветвление или переназначение переменной. Анализ намеренно консервативен: учитывает все Data-аргументы вызова и не доказывает безопасность извлечения поля из временного родителя. Ссылочные поля остаются неизменяемыми после конструктора; числовые элементы доступны для изменения. Владение и срок жизни входа сохраняет caller. Это внутренний raw module ABI, а не поддержка `.persist` или новых runtime handles. ELF entry должен возвращать скаляр; возвращающие Data процедуры вызываются другими процедурами или через внутренний ABI. Публичная точка входа module ABI начинает отдельный вызов с нулевым error-словом (байт128); после возврата caller проверяет этот статус. Внутренние вызовы продолжают распространять ошибки. `loan_update` показывает изменение входных данных с возвратом той же ссылки; выход за границы не записывает элемент. Это не транзакция: более ранние успешные записи функции автоматически не откатываются.

`sys.scratch(function, bytes, input...)` передаёт входы в существующий временный регион. Входные объекты должны быть плоскими: массивами/тензорами чисел или структурами без Data-полей. Они принадлежат вызывающей функции, а временные объекты callback освобождаются при выходе. Значения входов вычисляются слева направо до ограничения/отметки региона; результат не может быть Data. Запрет raw views и динамических native-вызовов внутри callback сохраняется. `sys.read_only` пока сохраняет прежнюю форму без входов. Пример scratch-inputs выполняет1000 изменений одного входного буфера при64 байтах временного бюджета; совпадает в VM и native ELF.

Рабочие буферы именно компилятора расширены: ScalarSource256KiB, ScalarBytes1MiB, host workspace32MiB (байты представлены словами i64). Их размеры берутся из типов/реальных буферов; module_prepare сохраняет явный лимит256KiB. Это не увеличение пользовательской activation arena или бюджета одного VM-шагa. Native self-build использует QEMU256MiB вместо128MiB для выросшего compiler workspace; обычные runtime тесты сохраняют128MiB.

Индексирование разбито на module_index_begin/module_index_step, emission — на module_prepare/module_emit_next. Обычные module_index/module_emit вызывают эти же шаги, второй реализации нет. Предварительный обход типов идёт порциями по512 шагов сканера, затем индексируется одна декларация; emission обрабатывает одну функцию. Незавершённая сборка не линкуется. Общий fuel внутреннего вызова не сбрасывается; временный регион возвращается при выходе.

Исходный объект компилятора хранится шестью физическими частями `projects/MiraOS/compiler-{lexer,parser,types,x86,module,data}`. Это те же вложенные определения одного `compiler @258`, без импортов, копий и новых runtime-ячеек. Чтение по имени/ID собирает нужный объект из общего индекса; bootstrap встраивает эти же части и собирает их тем же source_tree, не требуя checkout при запуске.

`compiler.aggregate_encoding` генерирует обычные native-инструкции для полей, индексов, инициализации, выделения/выравнивания, обнуления и проверок typed views. Там же генерируются разрешение tagged persistent handles через активный банк и барьер опубликованной записи. Это действующий путь native/kernel/UEFI backend, а не отдельный экспериментальный компилятор. Общие типы/layout, порядок выражений, scopes, fuel и связывание traps/state остаются прежними; Rust-адаптер подставляет проверенные layout-константы и цели исправлений. Примеры `examples/bootstrap-data`, `examples/aligned-data`; целевые проверки bootstrap_native и native_abi/aligned_aggregates, native_region_handles. Полный разбор записей и других агрегатов в переносимом frontend пока не реализован; ограниченные массивы доступны через module-профиль выше.

Самосборка: `cargo run --offline -p mira-lang -- build-compiler target/mira-compiler`. Получаются `code` (x86-64), `source` (настоящий вложенный compiler @258) и `index` (ID, входы, контрольные суммы и точки входа). Это образ компиляторного ядра под его внутренний ABI16 входных слов + ошибка128; это не готовый ELF, ядро ОС или замена публичного ABI программ. Data-аргументы этого внутреннего ABI — raw-адреса подготовленного workspace, не tagged handles общего runtime. Rust предоставляет VM первого поколения и файловый ввод/вывод; разбор входного исходника, проверка, emission и связывание делает Mira. Чужой каталог проекта builder не перезаписывает.

Проверка `cargo test -q --offline -p mira-lang --lib mira_compiles_its_typed_compiler_source_without_word_lowering -- --ignored` выполняет этот же сборщик, загружает полученный компилятор в UEFI и поручает ему пересобрать свой настоящий вложенный исходник. Сравнивается весь машинный код, затем второй экземпляр генерирует/исполняет новые функции и компилирует/запускает настоящий тензорный пример без host lowering. Прежний harness с подготовкой word-проекций удалён. Все113 определений кода/17 типов принадлежат одному compiler @258; отдельной копии реализации нет. Полный frontend Mira, графовая композиция и часть системных/тензорных runtime-операций пока остаются на Rust; всю MiraOS из native-редактора этот компилятор ещё не пересобирает.

### Первые компоненты интерфейса

`display.widgets.text_block(value,output)` и `integer_field(label,value,output)` формируют обычный Text в переданном буфере; результат — тот же буфер. Его владелец — вызывающий код/экземпляр, общей скрытой строки нет. В графе подключите нужные входы стрелками, как в `examples/interface-graph`. Этот пример — состав интерфейса в общем контексте определений widgets: тест подставляет именно определения из текущей MiraOS, а не их копию. Отдельный файл примера без этого контекста не является самостоятельным приложением.

`WidgetView(column,line,width,height,foreground,background)` задаёт прямоугольник в текстовых ячейках (символ8×16 пикселей); цвета — RGB0xRRGGBB. `display.paint(surface,view,text)` выводит в переданный Console, переносит строки, ограничивает область экраном и очищает остаток прямоугольника при укорочении текста. Размеры≤0 ничего не рисуют; отрицательные координаты прижимаются к0. Вывод ASCII, текст до96 байт; это ещё не Unicode, window manager или интерактивный визуальный конструктор. Сигнатуры — обычные типизированные порты Mira, код компонентов доступен для изменения.

В native обзоре числовые строки используют те же integer_field/paint; палитра выводит тем же paint собранные строки без предварительного очищения окна. Графовый пример проверяет композицию и свойства без экрана; фактический вывод проверяется графическим QEMU. В редакторе ограниченный source run пока не подключает общий графовый frontend/cells.*, поэтому не считать этот пример доступным через source run без подготовки контекста.
