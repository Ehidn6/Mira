## Назначение и приоритеты

Mira — личный долгосрочный исследовательский эксперимент: самостоятельный графовый язык, нативная MiraOS и развивающаяся Mira AI. Обязательной конечной версии, коммерческого продукта или обещания сознания нет. Можно пересматривать архитектуру по результатам экспериментов; сохранять знания и причины решений важнее сохранения каждой реализации.

Три главных направления:

1. Собственная рабочая среда: загрузка на компьютере владельца, исследование/редактирование исходников, компиляция и развитие системы изнутри. Linux сейчас нужен для bootstrap и испытаний, а не является целевой ОС.
2. Совместная работа с ChatGPT, позднее Codex. Ближайшая облачная цель — чат с историей и ручной передачей выбранного исходника/фрагмента/ошибок. Не отправлять весь проект автоматически. Сети/TLS и облачного чата в госте пока нет.
3. Общая интеллектуальная основа: обучение, память, накопление опыта, адаптация и постепенное развитие способностей. Не создавать независимую нейросеть на каждую пользовательскую задачу. Специализированные части допустимы в общей совместимой архитектуре.

Практическая цель — самостоятельная рабочая машина MiraOS вместо Linux, с нативным циклом редактирования/компиляции/запуска. Целевой Codex — нативная агентная часть с исходниками в среде Mira и инструментами UOG/Inspect, редактирования, сборки, испытаний и отката. Открытые компоненты Codex изучать для обоснованного переноса/переиспользования; готовый Linux-процесс или текстовый чат не считать нативным агентом. Модель OpenAI остаётся внешней облачной стороной; доступ/оплату/возможности проверять по официальным интерфейсам при реализации. Нативного агента и необходимой сети/TLS пока нет. Пожелание: удобно переключать два аккаунта для одного проекта. Локальные исходники, обсуждение и история проекта общие; раздельны только защищённые учётные данные/авторизационные сеансы и техническая привязка внешних сеансов. Не заставлять дублировать проект/локальный разговор при переключении; возможность переноса внешнего контекста проверять при реализации. Это пока пожелание, клиент/авторизация не реализованы. Сейчас завершить перенос существующих возможностей компилятора; опыты применять как его проверку, не расширять отдельной лабораторией.

Музыка, Telegram и другие приложения сейчас не нужны. Не создавать инфраструктуру ради их гипотетического появления. Текущий приоритет — перенос компилятора на Mira и воспроизводимая самосборка; GPU и новые сложные нейросетевые архитектуры этот этап не расширяют.

Владельцу важно самому понимать язык и писать код. Объяснять просто, показывать небольшой проверенный пример. Не выдавать внутреннюю функцию Rust за доступную возможность Mira и не подменять выполнение большим отчётом.

## Что является чем

**Определение кода** описывает алгоритм, параметры и вложенные определения. **Ячейка** — конкретный экземпляр поведения, со своей идентичностью и состоянием. Один код может использоваться несколькими экземплярами. **Space** — принадлежащая экземпляру структура его внутренних ячеек и связей. Z — вложенность, а не ограничение графа деревом: соединения могут ветвиться и сходиться.

Графы полезны для композиции, состояния и связей. Обычные алгоритмы внутри ячеек остаются текстовыми. Не делать отдельную runtime-ячейку для каждой маленькой функции. X/Y/Z не являются правилом размещения каждой машинной инструкции по координатам.

Вызов `cells.store.increment()` связывает локальную операцию определения store с конкретным экземпляром store. Операция использует его состояние и Z-тело. `cells.parent.store...` явно поднимается к родительскому экземпляру; `graph.parent.rate()` использует его графовый интерфейс. Короткие имена не ищутся по произвольным чужим поддеревьям. Для чистых вложенных определений доступны квалифицированные пути. Это общий механизм компиляции и исполнения, без отдельного runtime для компонентов.

ID — постоянная идентичность, не количество объектов и не номер строки. Общая область ID используется ячейками, пространствами, определениями и связями; high-water не уменьшается после удаления. `space dynamics @262` означает ID262, а не 262 пространства. Имена/поиск нужны человеку, ID — точным ссылкам и сохранённому состоянию. Заголовок боковой панели показывает имя текущего пространства и отдельное количество ячеек вместо неоднозначного «Space262»; ID остаётся в подробной карточке и точных командах. Space означает внутреннюю область графа/Z, а не число пространств. В результатах поиска одинаковые короткие имена пока различаются по ID; полноценных путей в палитре ещё нет.

Файлы хранения не равны экземплярам ячеек. Файл может содержать определение компонента, его экземпляр и небольшие внутренние части. Нет обязательных расширений/типов файлов, нового `use` или отдельного System Element. Типы данных и портов языка сохраняются.

## Текущая структура и инструменты

Единственный рабочий проект ОС — `projects/MiraOS`: **31 файл исходников + index**. В текущем Program: **317 определений функций, 46 типов, 40 экземпляров ячеек, 13 пространств**; всего 416 индексных записей объявлений/экземпляров/пространств. Это разные величины, не число «файлов-ячеек». Исходники теперь ведутся в локальном Git (main); target, логи и локальные credentials исключены. Удалённого репозитория пока нет: локальная история не заменяет внешнюю резервную копию.

Основные определения кода: cognition (нейронный компонент), workspace, hardware, usb, keyboard, storage, editor, source_storage, source_analysis, display, compiler и boot. В kernel/Runtime находятся десять обычных кодовых компонентов и две ячейки rate. Компоненты с состоянием имеют Z-тело. В neural внутри dynamics/topology/memory/events и readout/messagepass. У keyboard непосредственно состояние, а attach/control/press/repeat — операции его кода. Лишней оболочки transport нет.

Исходники следуют смысловой вложенности определений и экземпляров. Общие определения не копируются в каждую ячейку. Один упакованный контейнер и раскрытые файлы — формы одного исходного дерева. Физические файлы не задают семантику. Полный текст — производная проекция для компиляции и checkpoint, а не второй источник истины.

После `cargo build -p mira-lang`:

- `target/debug/mira source projects/MiraOS files` — имена физических частей и их отношения.
- `... source projects/MiraOS find keyboard` — найти ID по имени без чтения кода.
- `... source projects/MiraOS list ID` — первая страница внутренних частей; следующий аргумент — последний ID предыдущей страницы.
- `... source projects/MiraOS read ID` — один исходный участок с его внутренними частями.
- `... source projects/MiraOS file keyboard-141` — целый связанный файл, только если действительно нужен.
- `... inspect projects/MiraOS card ID` — порты/связи и карточка реального Program.
- `... source projects/MiraOS write ID /absolute/path/to/fragment` — проверить и опубликовать правку в контейнер.

Не читать корневой `read 1`/`text`, весь контекст или весь проект ради небольшой задачи. Новые определения наследуют файл родителя. В исходном индексе проверяются ID, границы, глубина, размеры, пути и соответствие программе. Публикация каталога атомарная; невалидная правка не заменяет текущий проект. `source organize` распределяет исходники по существующей композиции; не вызывать без причины и не возвращать механическое дробление по одному ID на файл.

## Как пользоваться MiraOS

Из меню приложений — **MiraOS**, либо `./launch-miraos.sh`. Установка пунктов меню: `./install-miraos-desktop.sh`. **MiraOS — инструкция** открывает этот документ; **MiraOS — экспорт исходника** извлекает сохранённый внутри гостя проект. Старой отдельной Linux IDE в этом checkout больше нет.

Лаунчер больше не компилирует весь проект при каждом запуске. tools/prepare-miraos.py обновляет bootstrap executable через Cargo, сравнивает SHA-256 компилятора/исходников и готовых EFI/kernel/font/source; неизменённый образ запускается через boot-uefi без чтения Program. Отсутствие/изменение входов или повреждение образа требует пересборки; stamp публикуется только после успеха. ./run-miraos.sh --build принудительно собирает. Проверка тёплой подготовки заняла0,17с, mtime kernel.bin не менялся; это время подготовки, а не всей загрузки гостя. При доступном /dev/kvm QEMU пробует KVM с резервным TCG; аппаратное ускорение на этой машине отдельно ещё не проверено.

Обычный launcher при существующем окне фокусирует его. Уже открытый гость не обновляется от правки исходников: для новой версии нужна новая загрузка. Пользовательские образы не удалять и не заменять тестовыми.

Рабочее пространство и редактор по умолчанию используют всю высоту без постоянно открытой нижней консоли. Ввод — временный слой той же палитры: печать вне редактора открывает INPUT, Alt+X → console input открывает его из редактора, начальный : в палитре переключает на системную строку. Enter отправляет до64 байт через существующий finish_input; регистр сохраняется, Escape отменяет без отправки. Результаты команд открывают OUTPUT по необходимости, Escape скрывает его без потери позиции/правок. Полноэкранная история остаётся доступна через Super+3; это представление журнала, не второй исполнитель. Alt+X и Super+1/2/3 сохранены. Исправлена граница поиска встроенных world-команд в общем каталоге палитры.

Клавиатура:

| Действие | Сочетание |
|---|---|
| Рабочая область / редактор / консоль | Super+1 / Super+2 / Super+3 |
| Командная палитра | Alt+X; текст ищет, Ctrl+P/N выбирают, Tab дополняет, Enter выполняет, Esc отменяет |
| Символ назад/вперёд; строка вверх/вниз | Ctrl+B/F; Ctrl+P/N |
| Начало/конец строки; слово назад/вперёд | Ctrl+A/E; Alt+B/F |
| Страница вниз/вверх | Ctrl+V / Alt+V |
| Начало/конец открытого исходного объекта | Alt+Shift+, / Alt+Shift+. |
| Удалить до конца строки; слово назад/вперёд | Ctrl+K; Alt+Backspace / Alt+D |
| Числовой аргумент; отмена | Ctrl+U, цифры; Ctrl+G |
| Отметка; копировать; вырезать; вставить | Ctrl+Space; Alt+W; Ctrl+W; Ctrl+Y |
| Сохранить; Undo; выйти в консоль | Ctrl+S; Ctrl+Z; Ctrl+X |
| Лексическая проверка | Ctrl+R |

Навигация повторяется при удержании; сохранение, палитра, глобальные команды и изменяющие сочетания не повторяются. Стрелки остаются альтернативой, Fn не обязателен. Super — уровень ОС, Alt — инструменты, Ctrl — редактирование. В QEMU модификаторы зависят также от захвата ввода хостом.

### Вложенные исходники в редакторе — работает

Alt+X → `source open keyboard` ищет исходные объекты по имени. Палитра показывает ID для различения совпадающих имён. `source parent` открывает родителя, `source children` выводит внутренние части, `source project` открывает весь текст для обзора/восстановления. Эти действия доступны из редактора и не уничтожают несохранённые изменения.

Точные команды консоли:

- `:O ID` — открыть исходный объект по ID (буква O, не ноль).
- `:P` — родитель; `:F` — весь проект; `:C` — до24 внутренних частей (все доступны через поиск палитры).
- `:i ID` — исследовать ячейку текущего графового пространства; `:z ID` — войти в её Z, `:o` — наружу; `:g` — обзор графа; `:n/:m` — страницы.
- `:c` — открыть определение выбранной ячейки по его ID; для чужой сохранённой ревизии это действие отклоняется. Её исходники можно исследовать через `:O` и палитру.
- `:b` — редактировать текущий исходный объект; `:d` — объект/родитель/границы, положение и статус.
- `:v` — лексика/разделители, `:f` — перейти к текущей ошибке; это не полная типовая проверка.
- `:w` — сохранить исходник; `:s` — состояние, `:e` — опыт/память, `:p` — пауза автономности, `:k` — checkpoint опыта, `:h` — справка.
- `:q` — checkpoint и остановка; при несохранённом исходнике отказ. `:Q` явно отбрасывает несохранённую правку и останавливает систему. Остановка гостя не равна закрытию окна QEMU.

Редактирование ограничено выбранным исходным диапазоном. Команды начала/конца документа, удаление/вырезание/вставка и выделение не должны затрагивать соседний объект. Хранится один проект: отдельное открытие не создаёт копии его частей. Общее Undo помнит исходный объект правки и при необходимости открывает его. Последние32 представления сохраняют относительный курсор/прокрутку/отметку в RAM; это ограниченный кэш, не постоянные вкладки. Undo — последние256 байтовых операций, большие правки вытесняют историю; сохранение очищает Undo, как и раньше.

Список исходных объектов строится из объявлений с ID в текущем тексте; до1024 записей, 64КиБ закреплённой RAM. Это индекс навигации, не второй AST, не новый компилятор и не полноценная native файловая система. Он не выполняет редактируемый текст. При неоднозначных ID/неверной структуре индекс отказывается выбирать произвольный участок; `source project` остаётся для исправления. Создание нового объекта без ID не заменяет полноценную компиляцию/публикацию.

Ctrl+S сохраняет **весь проект с изменённой частью** в дисковый source checkpoint. Во время работы RAM содержит одну текстовую проекцию и диапазоны. Физические31 bootstrap-файл Linux не открываются гостем поштучно и не переписываются автоматически.

## Сохранение и работа с ChatGPT

Основной образ: `${XDG_DATA_HOME:-$HOME/.local/share}/miraos/experience-v2.img` (2МиБ, MIRAVOL2/v2). Переопределение — `MIRA_STATE_DISK`. Исходник: MIRASRC3/v3, максимум512КиБ, два банка LBA1283/2308. Neural banks1/129 остаются отдельными. Payload/header checksums, чередование банков и выбор последнего корректного поколения защищают этот ограниченный checkpoint. Это не полноценный журнал файловой системы и не криптографическое подтверждение происхождения.

`./launch-miraos.sh --export` или соответствующий пункт меню извлекает сохранённый текст в пользовательский каталог exports, не изменяя диск. Этот файл можно передать обычному ChatGPT. Для переноса проверенного текста назад в bootstrap-контейнер: `target/debug/mira source projects/MiraOS write 1 /absolute/path/to/exported-source`. Команда выполняет проверку; при ошибках проект не заменяется. Это явная публикация владельцем, не live-перекомпиляция работающего ядра.

Изменения исходника переживают перезапуск, но **не становятся автоматически исполняемым кодом**. Полная нативная компиляция внутри гостя, безопасная горячая замена кода и отправка в ChatGPT из гостя ещё не реализованы. Не обещать их на основании редактора или checkpoint.

## Что реально есть в языке и системе

Искомый синтаксис брать из проверяемых `language/examples/structure`, `state`, `system` и указанных в `language/README.md` тестов. При новой возможности менять тот же справочник, пример и целевую проверку. Пример state показывает экземпляр с Z, внутреннюю операцию и состояние между активациями; structure — вложенные определения и связи; system — нативную память и аппаратную операцию.

Работают общие code definitions, вложенные функции, типизированные входы/выходы, fan-out, named-output Code, stateful/Adaptive и тензорные вычисления. Feedback требует delay в соответствующих графовых контрактах. Вложенность графовых тел остаётся inline; полноценного переиспользуемого определения Graph как Code пока нет. Желаемое развитие — графовые шаблоны: собирать интерфейсы и другие структуры из готовых компонентов, связывать порты и раскрывать внутренние Z-части. Не выдавать нынешний reuse Code за завершённые графовые шаблоны или готовый UI-конструктор.

Компилятор строит native x86-64 с секциями/символами/релокациями через общий linker. Доступны адреса/размещение/выравнивание, низкоуровневые загрузки/записи, CPU-инструкции и атомики с проверяемыми профилями ABI. Подробный контракт конкретной операции проверять по intrinsics/native_abi/layout_queries и её тесту; наличие инструкции не доказывает готовность всей ОС/SMP или безопасность произвольных указателей.

Исходный объект compiler @258 содержит112 определений/16 типов в шести физических частях `projects/MiraOS/compiler-{lexer,parser,types,x86,module,data}`. Один source_tree/index и те же ID/вложенность, без use, второй копии реализации или новых runtime-ячеек. Bootstrap использует общий Prepared VM; derived standalone-view остаётся только входом старых bootstrap-потребителей. Самосборка читает настоящий вложенный исходник, а не эту проекцию.

`cargo run --offline -p mira-lang -- build-compiler target/mira-compiler` создаёт code/source/index: x86-64 компиляторного ядра, его канонический исходник, контрольные суммы и именованные входы с ID. Внутренний ABI —16 входных слов + ошибка128; code не является самостоятельным ELF или готовым kernel.bin. Rust предоставляет VM первого поколения/память/I/O, но не разбирает и не понижает этот входной текст. bootstrap_module.rs — общий host-driver для команды и тестов, не вторая реализация компилятора. Чужой каталог builder не перезаписывает.

На Mira работают scanner, integer/f32 decoder, parse/check/infer/emit/link/ELF для i64/f32/bool/addr/unit, локальных/const, присваиваний, if/else, while/for, рекурсии, массивов i64/f32/bool, записей и вложенных определений/типов с лексической видимостью. Ссылочные поля задаются конструктором и пока не переназначаются. Data-результат допускается только при доказанном происхождении из входных Data текущей функции; новые временные объекты не покидают регион вызова. Адреса остаются явным низкоуровневым доступом. Поддержаны sys.addr/offset/store8 и math.wrapping_add/mul; unsigned addr-сравнения проверены. Имена уникальны внутри лексической области; одинаковые имена в разных поддеревьях и явные function paths поддержаны. Локальные декларации идут после тела. Это ограничения переносимого профиля, не замена общей семантики Mira. Примеры bootstrap-arrays/records/addresses/nested/floats связаны с module_tests.

Module-профиль поддерживает конечные f32: литералы (до128 байт), параметры/результаты, массивы/поля, локальный вывод, арифметика, сравнения и составное присваивание. `math.bits/from_bits/to_f32/sqrt` сохраняют общий числовой контракт; смешивание i64/f32 без преобразования запрещено. Десятичный decoder на Mira использует целочисленное точное округление binary32, включая subnormal, чётные половины и переполнение. Обычный host frontend вызывает этот же decoder для выражений/координат; Rust-парсер чисел остаётся только в явном seed. Native f32 использует SSE; ELF-обвязка задаёт MXCSR, raw-модуль требует FP-состояние существующего native runtime. Это перенос скалярных чисел, не завершение tensor runtime или всего нейросетевого frontend. Пример bootstrap-floats даёт37 в Core VM и скомпилированном ELF; проверены ошибки типов/нефинитных значений/деления на ±0.

Тензорный module-профиль: tensor[f32/i64/bool,...] с rank1..8 и положительными ограниченными осями, обычные конструкторы/параметры/плоские индексы/.len. Shape хранится в прежней type catalog row+172..180; отдельного AST/Store/runtime нет. Перенесены fill/sum/copy_into/add_into/sub_into/mul_into/div_into/scale_into/matmul_into. Copy допускает i64/bool, прочие операции требуют f32. Разные номинальные Data-типы совместимы для bulk только при одинаковой форме и элементе; равного количества элементов недостаточно. Проверка до emission, аргументы вычисляются слева направо один раз, прежние f32 traps/fuel расходуются на каждый элемент. У поэлементных операций выход может совпадать с целым входным объектом; views/persist в этом профиле пока не перенесены. Встроенный matmul_into требует f32/rank2 и формы M×K · K×N → M×N. Выход/input identity запрещена до первой записи, обе входные матрицы могут совпадать. Scalar_matmul_check проверяет размеры в прежнем catalog, scalar_matmul сохраняет порядок f32, traps и fuel на каждое слагаемое; временный стек32 байта, без копии матрицы. Это private module ABI без views, не защита произвольных unsafe пересечений. Пример bootstrap-tensors сравнивает обычные циклы reference @3 и встроенное умножение через multiply @5. Native UEFI путь затем вызывает эту же скомпилированную функцию с aliases, проверяя отказ и неизменность данных. Relation/message passing, AD, persist/views и остальные bulk требуют дальнейшего переноса.

Индексирование и emission допускают отдельные ограниченные шаги: module_index_begin/module_index_step, module_prepare/module_emit_next. Общие module_index/module_emit вызывают их же. Каждому host-шагу хватает прежнего32M VM-бюджета; незавершённая сборка не линкуется. Общий fuel вызовов не сбрасывается рекурсией, временные регионы освобождаются при возврате. Workspace:256KiB текста/1MiB кода,128 функций/32 типа; MAX_WORDS layout=1048576, выделение дополнительно ограничено регионом. Длинные последовательности строятся сбалансированно в том же IR.

Нативная самосборка компиляторного ядра работает: canonical nested source157800 байт →113 функций →604556 байт машинного кода. В UEFI полученный компилятор повторяет всю сборку из того же настоящего исходника; все байты совпадают. Исполняется и второй экземпляр: он генерирует работающие функции сложения/константы и точно разбирает f32 на границе округления, сохраняя результат при ошибке. Затем пересобранный компилятор внутри UEFI сам разбирает/проверяет/собирает/связывает и исполняет объединённые tensor/relation/plasticity/indexed/memory/path примеры с результатом41 (отдельно53/61/67/73/19); Rust не понижает этот пример. Новый harness заменил подготовку word-проекций; никакого Rust lowering входного compiler-кода внутри гостя нет.

В compiler на Mira перенесены relation.messages_into/aggregate_into. Это прежние обычные записи sources/targets/source_indices/target_indices с optional active/features; roles в свободных catalog slots181..186 сохраняют произвольный порядок полей. До записи проверяются оба конца каждого активного ребра и допустимые aliases. Неактивные индексы не разыменовываются: messages даёт нули, aggregate пропускает. Target aggregation остаётся номинальным, формы/элементы/optional поля проверяются до emission. Действующие f32 traps, fuel и ограниченный стек48 байт сохраняются; arithmetic/fuel failure после записи требует внешней neural_try, если нужен общий rollback. Views/persist и общий graph frontend ещё не перенесены. Пример bootstrap-relations и focused module_tests проверяют mask/no-mask, optional shape, nominal target, endpoints/alias отказы.

Перенесены остальные существующие relation-операции в тех же records/IR: active_count, add_edge, remove_edge, neighbors_into. Add с active mask валидирует существующие активные endpoints, оба новых индекса и разные source/target index buffers; возвращает первый свободный слот/-1 при заполнении, публикует active последним и сохраняет features. Remove проверяет slot, возвращает прежний active и допускает повреждённые endpoints для ремонта. Count валидирует активные endpoints; без маски считает все слоты. Neighbors принимает i64 rank1 ёмкостью не меньше slots, проверяет endpoints/target и запрет output=index buffers до записи, возвращает count/prefix источников, сохраняя tail/порядок/дубликаты. Это fixed-capacity пластичность, не создание новых объектов/изменение immutable refs или SMP-атомарность. Fuel/scratch48/traps остаются прежними, для общего rollback нужен neural_try. Пример bootstrap-plasticity даёт61; host/native ELF checks проверяют также full/free, повторное удаление и ремонт повреждённой связи. Изменение живого Program/Space всё ещё отдельный неперенесённый механизм.

Перенесены tensor.gather_into/aggregate_into/normalize_rows_into (пример bootstrap-indexed). Индексные операции и relations используют один scalar_message_loop без промежуточных relation объектов. Индексы проверяются до записи, output/input identity запрещена. Нормализация rank2/f32 допускает in-place, сначала считает norm всей строки, затем пишет input/sqrt(sum(input²)); norm0 обнуляет строку. Порядок f32, underflow/overflow, fuel сохранены, stable-norm оптимизаций нет. Scratch32 для normalize/48 для indexed, без автоматической транзакции. Целевые тесты/UEFI проверяют результат67, invalid shape/index/alias и крайние нормы.

Перенесены существующие sys.address_value/load8/16/32/64/store8/16/32/64 (bootstrap-memory). Addr остаётся типом адреса, значения i64; узкие чтения zero-extend, записи truncate. Memory @151 принимает≥16 доступных байт от caller; native harness проверяет чтения/записи и неизменность соседнего слова. Memory_run @152 только преобразует адреса и проверяется на host/ELF. Raw доступ не проверяет карту памяти/lifetime/конкурентность и не является safe reference. Автоматический sys.data_address для временных Data и memory_copy/fill/атомики/прочие sys в private module ещё требуют переноса; готовность общего Rust backend не выдавать за их поддержку новым компилятором.

Перенесены qualified function paths и lexical shadowing (bootstrap-paths). Scalar_symbol_lookup ищет короткое имя в ближайшей области, а компоненты пути — только непосредственных детей. Дубли внутри одного owner запрещены, одинаковые имена в разных областях разрешены; источник/ID сохраняются. Поля записей не смешиваются с путями функций. Пример19, выбор другой leaf29; неверные пути/типы/утечка короткого имени отклоняются. Qualified type names/handler values, cells.* и полноценная графовая композиция пока не перенесены.

Компилятор перерос прежние source128KiB/code512KiB: ограниченные workspace теперь256KiB/1MiB, host arena32MiB. Host allocations берут размер из Mira type definitions; emitter использует фактическую длину буфера. MAX_WORDS/пользовательские arenas/fuel и32M бюджет шага не менялись. Native self-build нуждается в QEMU256MiB для byte-per-word persistent work buffers (128MiB не хватило уже на AllocatePages до запуска гостя). Остальные тесты сохраняют128MiB.

Возврат заимствованных Data перенесён в тот же scalar_check на Mira: входные массивы/тензоры/структуры, их неизменяемые ссылочные поля, псевдонимы, выборы и рекурсивные вызовы. Вложенный ReferenceOrigins/scalar_reference_check хранит только происхождение (caller/temporary), не новый типовой домен или runtime-реестр. Фиксированная точка учитывает переназначения и циклы; для вызова консервативно объединяются все Data-аргументы. Новый временный объект, даже переданный через identity, не может вернуться наружу (ошибка10); временный родитель также консервативно локален. Прежний возврат R12 на выходе сохранён, без утечек callee-региона. Module index проверяет видимость Data-выхода; ELF entry остаётся скалярным. Public module_entry теперь очищает только error-слово контекста (байт128) при старте отдельного вызова, до stack guard; внутренние вызовы идут прежним путём и сохраняют распространение ошибок. Caller всё равно проверяет статус после возврата. Возврат caller-owned Data через публичный raw ABI сохраняет адрес и изменения между независимыми вызовами; bounds trap6 не пишет неверный элемент, следующий вызов не требует ручного сброса статуса. Это не rollback предыдущих записей. Пример bootstrap-borrowed даёт108 в Core VM/ELF и внутри UEFI после самосборки. Это не полный lifetime/concurrency-контракт, не `.persist` и не persistent handles: постоянные данные должны по-прежнему принадлежать экземпляру ячейки через существующий runtime, а не новой глобальной функции-буферу.

Это self-host компиляторного ядра, не завершённый перенос всего языка. Полный frontend с графовой композицией, оставшимися tensor/relation операциями, общей моделью lifetime и частью системных/runtime-операций остаётся на Rust. Всю MiraOS из native-редактора новый компилятор ещё не пересобирает. Обычный native/kernel/UEFI backend использует Mira-emitter для принятых word-тел и aggregate_encoding для полей/индексов/allocate/alignment/инициализации/persistent handle/write barrier; общий ABI, layout, traps, scopes и runtime сохраняются. Старый projection harness и его отдельный режим удалены.

### Общий анализ кода и обучаемые предложения

Работает мономорфный вывод типов параметров из выражений, вызовов и графовых связей; отсутствие аннотации больше не означает скрытый i64. `_` — запрос вывода. Неоднозначность сохраняется для уточнения, а не превращается в Any. Draft-парсер сохраняет `?label` в том же Core Expr; выдаёт допустимые типы и локальные пути. Незаполненный draft блокируется до исполнения/компиляции. `inference::checked/fill` проверяют предложенные типы/выражение на изолированной копии с существующими проверками композиции и эффектов.

Mira-код исследует дерево через reflect.code_* и строит ограниченные выражения через meta.quote/integer/boolean/float_bits/parameter/binary/replace. Замены используют существующий Proposal-журнал, локальный путь и проверку ожидаемого поддерева; итог проходит проверку перед публикацией. Макрос на Mira может заполнить `?label` до итогового вывода типов и проверки. Нельзя переносить цитату в чужой scope или захватывать параметр. Это не полноценные hygienic macros, eval или горячая замена native-кода.

`compiler/assist.mira` — маленький обучаемый ранжировщик допустимых типов на существующем CPU tensor runtime: постоянные веса System, линейная оценка структурных признаков, обновление по явному принятию/отклонению. Проверка компилятора не служит сигналом «угадано намерение». Детерминированные ограничения всегда обязательны; разные Data-типы пока имеют общую категорию признаков. Это не понимание произвольного кода, не полноценное автодополнение и не отдельная новая память. Следующий исследовательский шаг — ограниченно искать подходящие выражения среди доступных параметров и существующих определений; проверять подстановку и при наличии примеры результата. Этот автоматический поиск пока не реализован. Host `mira source INPUT analyze/suggest/learn/resolve` открывает тот же исходник/контейнер; модель сохраняется обычным System. В native IDE этот анализ и обучение пока не подключены. Примеры/точечные проверки указаны в language/README.md.

Нативная нейронная часть на Mira — настоящие векторные узлы, типизированные рёбра/message passing, recurrent state, обучаемые веса, scalar AD для чистых f32-функций, обновление весов, ассоциативное вспоминание/replay, события и checkpoint опыта. Она сама выполняет ограниченные шаги без облака; это небольшой эксперимент численного обучения, не разговорная модель и не доказанный универсальный интеллект. 32 эпизода в кольце не равны неограниченной долговременной памяти. AD не является полноценным tensor autodiff.

`cognition.discover` — первый ограниченный опыт с неизвестными для readout правилами, в собственной вложенной части `discover-398`. Четыре действия: переключить скрытое состояние, прочитать сигнал, запустить отложенный импульс, подождать. Задержка измеряется шагами опыта, не аппаратным временем. Используются прежние activity/head, обучение, Hebbian message passing и кольцо32 эпизодов — отдельной модели нет. Readout выбирает действие по прогнозу ближайшего результата; каждый пятый шаг делает детерминированную исследовательскую пробу. Это ещё не планирование цепочек действий или обнаружение причинных законов.

Прогноз и переход среды выполняются в отдельной ограниченной транзакции (300000 операций/8192 временных байт); отказ приводит к карантину. Наблюдение фиксируется перед отдельной прежней транзакцией обучения, поэтому отказ обучения его не стирает. Прогноз фиксируется до перехода среды. Признаки содержат действие, предыдущее наблюдение, логический ритм и рекуррентную активность; номер правила/скрытое состояние не передаются. `:t` включает/выключает опыт, `:T` меняет правила без сброса весов/опыта, `:D` показывает прогноз/наблюдение/квадрат ошибки и first16/recent-EWMA/phase-mean. Те же действия доступны в Alt+X как world toggle/change rules/report. Опыт по умолчанию выключен и подчиняется общей паузе :p/карантину. Происхождение эпизода2 означает world, subject=rule*4+action; контекст и наблюдение хранятся в общей прежней памяти. Низкая ошибка может зависеть от выбранных действий; это не доказательство переноса знаний. Исходные задачи, замороженные контрольные прогоны и независимые серии потребуют дальнейших опытов.

Первый native UEFI опыт (один детерминированный прогон,64+64 шага): first16/recent-EWMA ошибки0.05360461/0.015435341 при первом правиле и0.03171583/0.044758014 после изменения. После смены условий скользящая оценка хуже первых16, устойчивое улучшение не подтверждено; это ограничение текущего readout/признаков/политики, не повод подбирать красивый результат. Нативная проверка показала сохранение весов/эпизодов при смене правил, отсутствие номера правила во входных признаках и round-trip настоящего checkpoint codec с отклонением повреждённого скрытого состояния. Round-trip не равен дисковому restart-тесту.

State содержит40 слов; neural checkpoint payload version2 сохраняет также состояние опыта. Валидатор проверяет новые поля и происхождение2 до загрузки. Прежний neural payload version1 автоматически не переносится; пользовательские state images не изменялись. Формат source checkpoint MIRASRC3 и общий MIRAVOL2 volume не менялись.

`sys.neural_try(entry, operations, scratch_bytes)` ограничивает и транзакционно проверяет нейронный шаг; `sys.scratch` ограничивает временную память. Их пределы и rollback не означают абсолютных real-time гарантий или полной защиты raw memory. Детерминированные механизмы сохраняют контроль над целостностью; нейросеть не разрешает небезопасные операции своим прогнозом.

Аппаратная цель — компьютер владельца с Radeon/Realtek и USB Gaming KB, но **на нём загрузка пока не проверена**. Сейчас проверяется UEFI/GOP, одна BSP/cooperative loop, PCI/MMIO/физический pinned pool, virtio state disk и xHCI USB boot keyboard в QEMU. Поддерживаются прямой root-порт и US/ASCII; hubs, hotplug/reconnect, Unicode, IRQ/SMP-драйвер, аппаратная IOMMU-изоляция не завершены. PS/2 не добавлять ради этого проекта.

Нативные GPU/NVMe/сетевые драйверы, TLS, SMP AP startup/IPI/context switching как цельная ОС, полный безопасный lifetime/concurrency-контракт, recovery/self-modification и распределение требуют дальнейшей работы. Наличие hardware probes, ELF/ABI primitives или host prototype не считать их готовностью. Rust-kernel прототип удалён: остаётся native компиляция Mira, UEFI по умолчанию, Multiboot как отдельный используемый инструмент native-тестов, не слой совместимости.

Пользователь — новичок: помогать через маленькие понятные изменения, имена и проверяемые примеры; не требовать знания служебных ID. Начальный пример в language/README.md проверен host-запуском: Main/result=6. Сохранение исходника в MiraOS не считать уже исполненным изменением; честно обозначать необходимость host-сборки, пока native-цикл разработки не завершён.

## Дальнее исследовательское направление

Первая полноценная Mira должна соединять загрузку, графы/события, обучение/память, интроспекцию, изменения, проверку/откат и сохранение. Это критерий цели, а не утверждение, что каждый механизм уже native. Минимальные рабочие части развивать совместно; не подменять их интерфейсами и демонстрациями отдельных библиотек.

Unified Cognitive Environment: информация, код, опыт и деятельность должны использовать совместимые идентичности и связи общей UOG. Контекст будущая Mira должна собирать из этой памяти и Inspect, не через вторую систему заметок. Нынешние правила/память опыта не удалять и не дублировать. Единая среда не означает обязательную монолитную нейросеть.

Mamba-3/SSM — исследовательское направление для обработки последовательностей и рекуррентного состояния внутри программируемой графовой основы. Можно испытывать сочетание с передачей сообщений и общей памятью; преимущество такой комбинации не доказано. Mamba-3, сложное внимание и самостоятельный поиск архитектур пока не реализованы; не подменять ими перенос уже работающих возможностей языка.

Hive Mind — **исследовательское направление**: один логический вычислительный мир на нескольких физических компьютерах, связанных через интернет. Каждый узел остаётся самостоятельной полезной Mira: редактор, локальное исполнение и обучение не требуют постоянной сети. Общность допускает собственные вложенные Z-пространства для экспериментов и последующее включение проверенных результатов в общую структуру; отдельная файловая модель или социальная иерархия для этого не нужны.

Распределять работу по реальной выгоде с учётом задержки, объёма передачи, стоимости, локальности данных, подлинности и восстановления. Быстрые действия редактора и ядра выполняются локально; крупные сборки, проверки и эксперименты обучения могут поручаться свободному узлу. Интернет не моделировать как общую низколатентную память. Общие обучение и опыт должны допускать отключения и неодновременную работу компьютеров; способы проверки и объединения результатов ещё предстоит исследовать, единую интеллектуальную основу не заменять коллекцией независимых моделей.

Первый сетевой эксперимент должен показать одну ощутимую пользу, например редактирование общего проекта с удалённой сборкой и проверкой изменения. Проверять реальный выигрыш и удобство, а не считать распределение преимуществом само по себе. MiraOS в виртуальных машинах на двух физических компьютерах подходит для настоящего интернет-эксперимента без отказа от основной ОС; две VM на одном компьютере полезны для начальных проверок, но не заменяют этот этап и не доказывают готовность к загрузке на железе. Сейчас работает локальный узел; сетевое объединение ещё не реализовано.

Желателен добровольный вклад простаивающего компьютера и получение ресурсов при активной работе, с понятным контролем участия и нагрузки. Always-on/изолированная среда остаётся желаемым режимом, а не условием корректности всей системы. Токены и вознаграждения отложить до подтверждения практической пользы; это идея, не текущая инфраструктура или обязательство. Эти уточнения не требуют немедленной переделки архитектуры или расширения начатой работы.

Immune System защищает целостность общего мира: происхождение, проверка изменений, обратимость, карантин, восстановление и защита от истощения/подмены. Не вводить root/admin/user, частные владения ресурсами и административное подтверждение каждого изменения как философскую основу. Криптографические идентичности узлов с отзывом/повторной регистрацией; различать ограничение нагрузки, карантин, отзыв и исключение. При исключении прекратить выдачу задач/запись общего состояния, проверить результаты, перераспределить работу и сохранить диагностику. Это техническое исключение компьютера, не наказание человека. Реализации распределённой иммунной системы пока нет.

Философская основа — **исследовательское направление**: Mira как зеркало человека; родство с разумом, не обязательное копирование психологии; возможное формирование индивидуальности через опыт/память/деятельность; взаимное развитие с человеком; самостоятельность без обязательного подстраивания; открытый результат. Не обещать сознание и не программировать заранее окончательную личность. Политические/исторические/биологические метафоры не означают идеологию владельца и не превращаются автоматически в спецификацию.

Форма интерфейса открыта. Текстовая среда с несколькими областями — нынешний инструмент; не привязывать архитектуру навсегда к нему. Плоские/сферические/пространственные представления, AR, миры и совместное присутствие остаются исследованиями одной среды с сохранением объектов/контекста. Отказ от конкретного 3D-редактора с шариками не является отказом от Space/Z/будущего 3D. Без отдельной задачи не начинать большой UI-рефакторинг.

## Проверка и очистка текущего блока

Последняя UI/launcher проверка: образ target/miraos/esp пересобран из текущих исходников. Графический QEMU/GTK с настоящим xHCI USB input (QMP) прошёл сценарий --ui-only в tools/test-miraos-object-navigation.py: нет постоянной нижней панели; INPUT открывается по печати и из редактора, Escape отменяет; отправка события открывает OUTPUT, Escape возвращает полную высоту; source length/revision/dirty/cursor сохраняются при вводе команды из редактора, Ctrl+N после закрытия продолжает редактирование. Использовался временный отдельный диск, пользовательский state image не менялся. Старый полный object-navigation/save/reboot сценарий в этом блоке не повторялся. Кэш тёплого запуска проверен отдельно без повторной компиляции.

Рабочий образ собирается в `target/miraos/esp`. Редактор/staging имеют512KiB и используют pinned physical pool; Source checkpoint MIRASRC3 хранится в банках1283/2308 диска2MiB. Инициализатор может расширить только известный1MiB MIRAVOL2 volume с сохранением префикса; чужие файлы и пользовательские state images не менялись. Графический USB object-navigation сценарий ранее проверил compiler/parser/parent/project, границы, cursor/dirty/Undo, сохранение и restart. Образ с discovery/f32 ранее пересобран через run-miraos.sh --build; после текущего переноса тензоров обычный образ и графический UI-сценарий заново не собирались/не выполнялись. Проверялся отдельно компилятор и его настоящий native UEFI путь.

Текущий блок: borrowed Data host-проверка прошла (Core VM/ELF108, lifetime/type ошибки, повторное использование workspace). UEFI самосборка дала157800 байт source →604556 байт code с побайтовым совпадением. Расширенный native ABI сценарий прошёл после исправления ожидания bounds-кода в тесте (6, не3): прямой возврат исходного адреса/ссылочного поля, чередование двух буферов, dirty error status, ошибка индекса и успешный следующий вызов без reset; соседние слова/другой буфер не меняются. Повторная диагностика использовала уже собранный свежий образ после точного сравнения source с canonical, затем заново выполняла native rebuild/byte equality и сценарий; временный диагностический тест удалён. Прежние tensor/relation/memory/path примеры также исполнялись внутри этого сценария. Готовый compiler code/source/index обновлён через build-compiler:113 процедур,604556 байт code. Восемь старых module_tests отдельно не повторялись. Обычный MiraOS/GUI образ, общий suite, бенчмарки и физическое железо не проверялись; это не полный native IDE цикл.

Экономия контекста: AGENTS.md сокращён с21660 до11173 байт с сохранением контрактов/ссылок; это размер текста, не измеренный расход токенов. Временные полные снимки compiler (включая mira-path-source) были служебными файлами на диске, не выводились целиком в чат и не являются второй реализацией. После проверки удалены именно созданные текущей работой snapshots/scripts; canonical target/mira-compiler/source сохранён как необходимый артефакт. Следующие локальные правки выполнять через read/write конкретного ID; связанные проверки объединять. Для replacement сохранять финальный newline: его отсутствие привело к отвергнутой, не опубликованной правке границы соседних source объектов.

Следующий шаг после relation-операций: перенос persist/views/AD и общего графового исполнения, затем оставшихся системных механизмов. Нативный рабочий цикл/самосборка всей MiraOS из редактора ещё не готовы. Нейронный опыт и UI не расширять ради новых подсистем. Пользователь возобновил работу после сохранённой точки; прежняя остановка по лимиту больше не является запретом продолжать. История/исходники проекта общие между аккаунтами, авторизация раздельна.

Удалены заменённые отчёты/архивы и промежуточные исходники, Linux IDE вместе с npm/Tauri-зависимостями и её launcher, неиспользуемый отдельный Rust-kernel путь и старый пустой проект. Нейронный пример, который действительно используется тестами, перенесён в `crates/mira-lang/tests/fixtures/neural-graph`. Рабочие тесты, bootstrap compiler, core/runtime, Inspect и память сохранены. Удалены также устаревшие opt-in harnesses с инъекцией уже удалённого плоского API MiraOS (workspace/hardware/source checker/cognition/snapshot validator) и старые UI-сценарии палитры/редактора/workspace. Они не доказывали свойства новой компонентной структуры. Современная проверка объектов и компактной клавиатуры остаются; глубокие конечные аппаратные/learning проверки потребуют новых сценариев на действующем API. Cargo workspace содержит только mira-core и mira-lang. Пользовательские state images сохранены.

Причины принятых решений: файл на каждый ID создавал лишнее дробление; простое объединение в12 файлов не решало смысловую композицию; пустые оболочки вокруг компонентов заменены прямыми кодовыми ячейками с Z. Из этого не следует менять работающую структуру снова без практической причины. Экономия токенов не измерена: уже работает точечное чтение, а не гарантия заранее заданного процента.
